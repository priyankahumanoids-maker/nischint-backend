# Support Ticket Draft: Production `backend` supervisor — drop `--reload`, raise `--workers` to 2

**For user to file via Emergent platform support channel**

---

## Subject
Production `backend` supervisor program: drop `--reload` and raise `--workers` to 2 (P0 — App Store launch blocker)

## Severity
**P0** — App Store submission for the Nischint mobile app is blocked on this fix. Two compounding production issues converge here, both confirmed via load test on 2026-05-30.

## Summary
The `backend` program defined in the read-only `/etc/supervisor/conf.d/supervisord.conf` runs uvicorn with **two settings that cannot coexist with a production launch**:
1. `--reload` — causes recurring 520 (Cloudflare timeout) outages every time a worker restarts on a file-watch event
2. `--workers 1` — single-CPU bottleneck. Load test at 60 concurrent users produced 94.75 % request timeout rate, with asyncio event-loop lag peaking at 2,228 ms (baseline ~0.1 ms)

Both fixes can land in a single supervisord.conf edit and a single redeploy.

## Current configuration (read-only — we cannot edit)

```
[program:backend]
command=/root/.venv/bin/uvicorn server:app --host 0.0.0.0 --port 8001 --workers 1 --reload
directory=/app/backend
autostart=true
autorestart=true
environment=APP_URL="https://077678dd-f708-463f-aba0-e72b011600b2.preview.emergentagent.com",INTEGRATION_PROXY_URL="https://integrations.emergentagent.com"
```

The header `# READONLY FILE, DO NOT EDIT THIS FILE` immediately above this block confirms we cannot fix this from our side — the conf file is owned by the platform.

## Requested change

Replace the `command=` line above with:

```
command=/root/.venv/bin/uvicorn server:app --host 0.0.0.0 --port 8001 --workers 2
```

Preview / dev environments may keep `--reload` for the iteration loop — only the production deployment surface needs this fix.

## Why this matters

### Issue 1 — `--reload` causes 520 outages
* `--reload` was a dev-mode default never intended for production. The watcher fires whenever any file in `/app/backend` mtime updates — log rotation, cache writes, scheduler temp files all trigger the same restart cascade.
* Each reload races inflight HTTP and WebSocket connections. Long-lived clients (Command Center WS, SSE streams) drop hard, surface as 520 on the edge.
* We've already split scheduler work into a separate process (`nischint-scheduler` program, `NISCHINT_ROLE=scheduler`) — so the `backend` program is genuinely API-only and has zero need for reload-on-write.

### Issue 2 — `--workers 1` cannot handle launch concurrency

Load test on 2026-05-30 against the running config produced these results:

```
Scenario              reqs  fails    p50      p95      p99      max
auth/me                149   134    10000ms  10000ms  10000ms  10241ms
guardian/dashboard      79    79    10000ms  10000ms  10000ms  10003ms
sos/trigger             22    21    10000ms  10000ms  10000ms  10138ms
health-signals/POST     48    48    10000ms  10000ms  10000ms  10004ms
Aggregated             305   289    10000ms  10000ms  10000ms  10241ms

Failure rate: 94.75 %
```

Critical runtime metrics during peak load:

```
metric                       baseline   peak      ratio
asyncio_loop_lag_ms          0.08       2227.94   ~28,000×
asyncio_task_count           10         358       36×
pg_pool_checked_out          0          19        (63% of 30 cap — healthy)
pg_pool_wait_count           0          0         (no DB contention)
memory_rss_mb                189.8      210.6     +11% (no leak)
file_descriptors             28         66        +136% (no leak — recovered to 38)
```

**Root cause**: single uvicorn worker means a single asyncio event loop. Any CPU-sync work (bcrypt password verify, JSON parsing of large payloads, sync DB drivers) blocks the entire request stream. The DB connection pool, memory, and FDs all stayed healthy — the bottleneck is purely CPU/event-loop, fixed by adding workers.

## Acceptance criteria

1. The `backend` program in `/etc/supervisor/conf.d/supervisord.conf` on production hosts has `--reload` removed AND `--workers 2` set.
2. `nischint.care` 520 rate drops to baseline (elevated 520 rate correlated 1:1 with uvicorn reload events).
3. A repeat 60-VU load test against production demonstrates p95 < 500 ms and error rate < 1 % on the same endpoint mix.
4. No regression in scheduler timing — the `nischint-scheduler` program continues to run unaffected.

## Additional context

* Nischint app architecture: FastAPI backend + PostgreSQL/Supabase + Redis + APScheduler.
* `NISCHINT_ROLE=api` is already set on the `backend` program (per the existing supervisord.conf).
* Phase 1 process isolation already ships in the codebase (see `/app/memory/PRD.md` "Phase 1 Process Isolation").
* Memory footprint per worker is ~210 MB peak — `--workers 2` lands at ~420 MB, well within the K8s pod's 8 GB limit (current `cgroup_mem_pct` is 27 %).
* Container has ≥ 2 CPU cores available — `--workers 2` is a true parallelism gain, not just contention.

## Reference logs / artefacts

* `--reload` correlation: lines matching `WARNING:  WatchFiles detected changes in '...'. Reloading...` in `/var/log/supervisor/backend.out.log`.
* Load test report and raw CSVs: `/app/memory/loadtest_report_2026_05_30.md` (full timeline, per-endpoint p50/p95/p99, runtime metric trace).

## Why we cannot redeploy our way out of this

We can already ship `--workers 2` in our own startup scripts if the supervisord.conf wasn't read-only. But because Emergent owns that file, every redeploy reverts to `--workers 1 --reload`. This is purely a platform-side config change — no code change required from us. We can run the post-fix verification load test the same day the change lands.
